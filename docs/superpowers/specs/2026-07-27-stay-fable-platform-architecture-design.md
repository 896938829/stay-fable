# Stay Fable 酒店与民宿预订平台架构设计

状态：已完成方案讨论，待用户复核
日期：2026-07-27
目标版本：MVP 至首年成长期

## 1. 项目目标

Stay Fable 是面向中国大陆用户的酒店、民宿和农家乐查询与预订平台。首期采用平台自营运营与轻量商家自助相结合的模式：

- 用户通过微信小程序搜索、查看、预订和支付。
- 支付宝、抖音小程序作为后续首发兼容端。
- 平台运营人员负责商户审核、房源内容、客服、营销和财务管理。
- 商家通过轻量 Web 后台维护房态、价格、订单和退款协作。
- 标准房型支持即时确认；特色民宿和农家乐支持商家人工确认后支付。
- 首期支持简体中文、英文界面和人民币结算。
- 首年目标规模为不超过 1,000 家商户、日订单 500–10,000。
- 首期团队规模为 1–3 人，因此优先降低开发、部署和运维复杂度。

## 2. 成功标准

### 2.1 产品成功

- 用户能够完成搜索、查看、报价、预订、支付、取消和退款闭环。
- 标准房型支付后能够即时确认，且并发下单不会超卖。
- 人工确认订单能够在商家确认后限时支付。
- 商家能够独立维护未来房态、每日价格和处理订单。
- 运营人员能够完成商户、房源、订单、营销、客服和财务工作。
- 用户可以在中英文之间切换，且中文内容缺少英文翻译时有明确降级行为。

### 2.2 技术成功

- 月度核心预订服务可用性目标不低于 99.9%。
- 支付回调、库存占用和退款操作具备幂等能力。
- 数据库恢复点目标（RPO）不超过 15 分钟，恢复时间目标（RTO）不超过 2 小时。
- 所有生产数据访问经过身份验证、权限校验和审计。
- 发布前满足 OWASP ASVS 5.0 Level 2 的适用控制项。

### 2.3 运营成功

平台的北极星指标为“成功入住订单数”，而不是注册数或支付订单数。运营同时关注房态准确率、商家响应时间、无房拒单率、取消率、退款时长、投诉率和复购率。

## 3. 范围与非目标

### 3.1 首期范围

- 微信小程序用户端。
- 支付宝、抖音小程序的平台适配能力和构建链路。
- 运营与商家共用的响应式 Web 管理后台。
- 房源、房型、价格日历、库存日历和政策管理。
- 搜索、筛选、附近房源和基础排序。
- 即时确认订单、人工确认订单、支付、取消和退款。
- 优惠券与基础营销位。
- 评价、内容审核、消息通知和客服工作台。
- 基础运营报表、埋点、日志、告警、审计和对账。

### 3.2 明确非目标

首期不建设：

- 原生 iOS/Android App。
- 多币种、跨境支付或海外部署。
- 完整 PMS、Channel Manager 或 OTA 库存直连。
- 复杂动态定价、AI 推荐或广告竞价系统。
- 微服务、Kubernetes、Kafka、Flink、Hadoop 或独立数据仓库。
- 商家自动分账、复杂佣金结算和电子合同全流程。
- 会员等级、积分商城、直播或社交社区。

这些能力只有在业务指标证明需要时再设计。

## 4. 总体架构

```text
用户小程序（微信 / 支付宝 / 抖音）
商家后台（响应式 Web）
运营后台（响应式 Web）
            │
      EdgeOne / WAF
            │
        HTTPS REST API
            │
NestJS 模块化单体
├─ 身份与权限
├─ 商户与门店
├─ 房源与内容
├─ 房型、价格与库存
├─ 搜索与排序
├─ 订单与入住人
├─ 支付与退款
├─ 优惠与营销
├─ 评价与审核
├─ 通知与消息
├─ 运营数据与审计
└─ 定时与异步任务
            │
PostgreSQL + Redis + COS/CDN
```

架构采用“多端前台 + 统一 API + 模块化单体 + 托管基础设施”。

模块化单体是首期有意选择，不是临时妥协。所有业务模块部署在一个应用中，但每个模块有独立的接口、应用服务、领域规则和数据访问层。模块不能绕过公开服务直接修改其他模块的数据。

当某个模块出现独立扩容、隔离或团队所有权需求时，才从单体中拆出。优先候选为通知任务、搜索和数据分析，而订单、支付和库存应尽可能保持事务边界清晰。

## 6. 前端设计

### 6.1 用户小程序

技术栈：

- Taro、React、TypeScript。
- TanStack Query 管理服务端状态。
- Zustand 管理少量本地界面状态。
- React Hook Form 与 Zod 管理表单和运行时校验。
- i18next 与 react-i18next 管理本地化。
- dayjs 处理日期展示。
- SCSS Modules 与 Design Tokens 管理样式。
- Vitest、React Testing Library 与平台真机回归。

首发顺序为微信、支付宝、抖音。业务页面尽量共享，平台差异通过统一接口隔离：

```text
PlatformAdapter
├─ login()
├─ pay()
├─ getLocation()
├─ openMap()
├─ subscribeMessage()
└─ contactService()
```

每个平台提供独立实现文件。业务代码不得直接调用 `wx`、`my` 或 `tt` 全局对象。

### 6.2 管理后台

商家与运营使用同一个 React Web 项目：

- React、TypeScript、Vite、Ant Design。
- TanStack Query、React Router。
- React Hook Form、Zod、i18next。
- ECharts 负责内部图表。
- Playwright 负责核心工作流端到端测试。

菜单由角色决定，但服务端权限校验始终是最终安全边界。

### 6.3 多语言

首期语言为 `zh-CN` 与 `en-US`。

- 界面文案按 `common`、`search`、`property`、`booking`、`payment`、`account` 等命名空间管理。
- 组件内不直接写展示文案。
- 日期、人数、金额和复数使用统一格式化工具。
- 房源名称、简介、设施和政策使用结构化翻译表。
- 缺少英文内容时显示中文原文，并明确标注尚无英文翻译。
- 用户手动设置优先于平台语言。
- 英文界面仍使用人民币结算。

### 6.4 前端防御

- 所有后端响应执行运行时结构校验。
- 页面统一处理加载、空数据、无权限、网络失败和未知错误。
- 仅幂等查询允许自动重试；订单、支付和退款不得由前端自动重试。
- 写操作使用幂等键并防止重复点击。
- 金额、库存、折扣和订单状态以后端为准。
- 本地不保存身份证图片、支付资料或完整入住人资料。
- 平台授权拒绝、接口不可用和旧版本都必须有明确降级界面。
- 功能开关支持按平台、版本和用户范围关闭功能。

## 7. 后端设计

### 7.1 技术栈

- Node.js LTS、TypeScript、NestJS。
- REST API 与 OpenAPI。
- Prisma ORM 与 PostgreSQL。
- Redis 与 BullMQ。
- Pino 结构化日志。
- Jest/Vitest、Supertest 和集成测试。

首期不采用 GraphQL。Prisma 负责常规访问与迁移；库存并发、PostGIS 和复杂统计允许使用参数化 SQL。

### 7.2 业务模块

| 模块 | 职责 |
|---|---|
| 身份（Identity） | 用户、平台身份、会话、角色和权限 |
| 商户（Merchant） | 商户、门店、资质、员工和数据范围 |
| 房源目录（Catalog） | 房源、房型、设施、媒体、政策和翻译 |
| 定价（Pricing） | 价格计划、每日价格、费用和报价快照 |
| 库存（Inventory） | 每日库存、占用、停售和库存调整 |
| 搜索（Search） | 条件搜索、附近房源、筛选和排序 |
| 预订（Booking） | 即时/人工订单、入住人、取消和状态历史 |
| 支付（Payment） | 平台支付、回调、退款、关单和对账 |
| 营销（Promotion） | 优惠券、活动规则和营销位 |
| 评价（Review） | 评价、商家回复和内容审核 |
| 通知（Notification） | 订阅消息、短信、站内通知和重试 |
| 运营（Operations） | 客服工作台、导出、审核和异常处理 |
| 分析（Analytics） | 业务事件、聚合指标和报表 |
| 审计（Audit） | 敏感操作与不可变审计记录 |

### 7.3 API 约定

- API 前缀包含版本，例如 `/api/v1`。
- 请求和响应使用统一封装结构，但流式下载除外。
- 每个请求返回 `request_id`。
- 错误包含稳定业务错误码，不暴露内部堆栈。
- 分页优先使用游标；后台小数据列表可使用页码。
- 创建资源支持 `Idempotency-Key`。
- OpenAPI 文档是前后端协议来源，生成客户端类型。
- 旧 API 至少保留一个小程序发布周期。

## 8. PostgreSQL 数据设计

推荐 PostgreSQL 17 高可用版，启用 PostGIS、SSL、自动全量备份和日志备份。

主要实体：

```text
user ─ user_identity ─ user_role ─ role_permission
merchant ─ property ─ room_type ─ room
              │          ├─ rate_plan
              │          ├─ daily_price
              │          └─ daily_inventory
              ├─ property_media
              ├─ property_i18n
              ├─ facility
              └─ policy

booking ─ booking_item ─ guest
   ├─ inventory_hold
   ├─ payment
   ├─ refund
   ├─ booking_status_history
   └─ notification

promotion ─ coupon
review ─ moderation_record
audit_log
event_outbox
analytics_event
```

数据约束：

- 金额以人民币“分”的整数保存。
- 技术时间戳使用 UTC；房源保存 IANA 业务时区。
- 房态按“房型 + 日期”建立唯一记录。
- 订单保存房源、价格、费用和政策快照。
- 平台身份与平台内用户主体分离。
- 交易表包含业务编号、版本号和审计字段。
- 房源位置使用 PostGIS `geography(Point, 4326)`。
- 软删除只用于需要恢复和审计的业务实体；支付记录不物理删除。
- 数据库迁移文件进入版本控制并在生产执行前审核。

## 9. 库存、报价与订单

### 9.1 报价

报价由后端生成并包含：

- 房源、房型、价格计划和入住日期。
- 每晚房费、优惠、服务费和总价。
- 取消政策和确认模式。
- 报价版本、币种和短期有效期。

创建订单时必须重新校验报价、库存和优惠。前端价格仅供展示。

### 9.2 即时确认

```text
重新报价
→ 按日期顺序锁定 daily_inventory
→ 校验每晚可售数量
→ 事务内创建订单和 inventory_hold
→ 创建平台支付单
→ 用户支付
→ 服务端验签回调或主动查单
→ 占用转已售并确认订单
```

并发控制同时使用：

- 按固定日期顺序获取行锁，降低死锁风险。
- 条件更新保证剩余库存非负。
- 订单号、支付单号和库存占用使用唯一约束。
- 事务失败时整体回滚。
- 短期库存占用到期后由任务释放。
- 定时查单与对账修复回调丢失。

Redis 锁只用于降低热点竞争，不能代替 PostgreSQL 事务。

### 9.3 人工确认

```text
用户提交预订申请
→ 商家确认房态和最终价格
→ 系统生成限时待支付订单
→ 用户支付
→ 系统确认订单
```

商家拒绝或超时则关闭申请，不提前收款。

### 9.4 状态机

订单状态至少包含：

- `PENDING_MERCHANT`
- `PENDING_PAYMENT`
- `PAID`
- `CONFIRMED`
- `CHECKED_IN`
- `COMPLETED`
- `CANCELLED`
- `REFUND_PENDING`
- `REFUNDED`
- `CLOSED`

状态只能通过明确的领域命令迁移，每次变化写入状态历史和审计日志。支付状态、退款状态与订单状态分别保存，不能混为一个字段。

## 10. 支付与退款

统一支付协议：

```text
PaymentProvider
├─ WeChatPayProvider
├─ AlipayProvider
└─ DouyinPayProvider
```

规则：

- 前端支付成功不能直接确认订单。
- 仅验签回调或主动查单能够确认收款。
- 创建支付、处理回调、退款和关单均幂等。
- 平台交易号、商户订单号和退款号建立唯一约束。
- 原始回调保存必要摘要和哈希，不保存不需要的敏感正文。
- 非法状态迁移必须拒绝并告警。
- 每日执行订单、支付、退款和结算对账。
- 支付密钥、证书和私钥存入 KMS/密钥管理服务。

## 11. 图片与文件

使用腾讯云 COS：

| 存储区 | 用途 | 访问 |
|---|---|---|
| upload-quarantine | 新上传待检测文件 | 私有 |
| property-public | 审核通过的公开房源图片 | CDN 只读 |
| secure-documents | 证照、合同和身份材料 | 私有短链 |

上传流程：

1. 客户端申请限制对象路径、类型和大小的短期上传凭证。
2. 客户端直传隔离桶。
3. 服务端校验文件头、解码、尺寸和内容安全。
4. 生成缩略图与现代图片格式。
5. 审核通过后发布到公开桶。

永久云密钥不下发客户端。敏感文件下载需要权限检查、短时链接和审计。

## 12. 部署与环境

```text
EdgeOne / WAF
      │
CloudBase Run
├─ api-server：生产至少 1 个常驻实例
└─ job-worker：生产至少 1 个常驻任务消费者
      │ 私有网络
├─ PostgreSQL 高可用版
├─ Redis 高可用版
├─ COS
├─ KMS / 密钥管理
└─ CLS / 监控告警
```

生产 API 和任务消费者都不缩容到零。API 按 CPU、内存和请求并发扩容，任务消费者按队列积压与任务等待时间扩容。

环境分为：

- 本地开发：本地容器依赖和脱敏种子数据。
- 预发布：独立云资源和支付沙箱/测试配置。
- 生产：独立数据库、Redis、COS、密钥和严格权限。

不同环境禁止共享数据库、对象桶、支付回调地址和密钥。

## 13. 运营体系

运营后台提供六个工作台：

| 工作台 | 主要职责 |
|---|---|
| 供给运营 | 商户建档、资质、合同状态、房源上线 |
| 内容运营 | 图片、标题、设施、政策、翻译和推荐位 |
| 交易客服 | 待确认、超时、取消、退款和投诉 |
| 营销运营 | 优惠券、专题、渠道、新客和复购 |
| 财务运营 | 支付、退款、结算和对账差异 |
| 风控审计 | 异常登录、刷券、价格突变和敏感操作 |

运营优先级依次为供给可信、房态可信、价格可信和履约可信。

基础排序由可订状态、搜索相关性、距离、房态准确率、转化、评分、取消率、投诉率和维护活跃度共同决定。付费推广必须明确标记。

## 14. 数据采集与分析

统一事件结构：

```text
event_name
event_version
occurred_at
anonymous_id / user_id
session_id
platform
app_version
page
property_id / room_type_id / booking_id
campaign
properties
```

首期事件覆盖打开应用、搜索、筛选、曝光、详情、日期、报价、申请、商家确认、支付、取消、退款、入住完成、收藏、分享和客服。

数据治理原则：

- 支付、退款、库存和订单状态使用服务端事件。
- 客户端行为事件允许丢失，不得影响交易。
- 分析事件不记录姓名、手机号、身份证、精确住址或支付密钥。
- 事件具有版本和数据字典。
- 不同环境数据隔离。
- 每类数据具有保存期限和到期处理方式。

首期数据链路：

```text
客户端事件
→ NestJS 接收
→ Redis/BullMQ 异步处理
→ PostgreSQL 月度分区事件表
→ 每日聚合表 / 物化视图
→ Metabase 私网仪表盘
```

交易指标直接从业务表生成。分析事件使用独立 schema 和受限数据库账号，聚合任务避开交易高峰。行为事件达到数千万级并影响 PostgreSQL 后，再评估独立分析库或 ClickHouse。技术日志进入 CLS，不能与业务分析事件混用。

## 15. 中间件

| 组件 | 用途 |
|---|---|
| Redis | 缓存、限流、验证码、幂等辅助和热点协调 |
| BullMQ | 超时、通知、图片、审核、对账和重试 |
| Outbox | 保证事务提交后异步事件最终发出 |
| EdgeOne/WAF | TLS、CDN、DDoS、WAF 和 Bot 防护 |
| COS/CDN | 图片、文件和静态资源 |
| CLS | 结构化日志、检索、审计和告警 |
| Metabase | 内部经营仪表盘 |
| OpenTelemetry | 请求链路、指标和错误上下文 |

首期不引入 Kafka、Elasticsearch 或自建 ELK。

## 16. 安全设计

### 16.1 传输

- 外部仅支持 HTTPS，最低 TLS 1.2，优先 TLS 1.3。
- Web 后台启用 HSTS、Secure、HttpOnly、SameSite 和 CSRF 防护。
- 数据库启用 SSL 并验证 CA。
- CORS 使用明确域名允许列表。
- 支付回调验证签名、时间戳、随机数并防重放。

### 16.2 身份与授权

- 小程序平台登录凭证只由后端换取身份。
- 使用短期访问令牌和轮换式刷新会话。
- 运营账号强制 MFA；商家财务和管理员强制 MFA。
- 密码使用 Argon2id。
- 授权使用 RBAC 与商户数据范围组合。
- 每次请求检查登录、操作权限、数据归属和业务状态。
- 默认拒绝，敏感操作二次确认。

### 16.3 敏感数据

- PostgreSQL 创建时启用 TDE，密钥由 KMS 管理。
- 身份证件等敏感字段使用应用层信封加密。
- 精确匹配使用独立 HMAC 索引。
- 后台默认脱敏，查看原文需权限和审计。
- 日志、事件、错误堆栈和导出禁止泄露敏感信息。
- 导出文件加水印、权限和自动过期。

### 16.4 服务器与云账号

- 数据库、Redis、任务进程和管理工具不开放公网。
- 源站仅接受 EdgeOne/WAF 或私有网络流量。
- 容器非 root 运行，使用最小镜像、只读文件系统和资源限制。
- 日常不用云主账号；CAM 子账号、角色和 MFA 落实最小权限。
- 应用通过云角色访问服务，不使用长期永久密钥。
- WAF 对注入、XSS、路径穿越、恶意文件和 Bot 流量设规则。
- 登录、搜索、报价、下单、支付回调和导出分别限流。

### 16.5 安全编码

- 输入执行类型、长度、枚举、格式和业务范围校验。
- 数据访问全部参数化。
- 所有资源查询携带商户范围，防止 IDOR。
- 订单和支付采用显式状态机。
- 外部 URL 使用白名单以防 SSRF。
- 文件校验真实格式、尺寸和内容。
- 富文本按允许列表清洗，普通文本转义。
- 生产错误不暴露内部实现。
- CI 执行依赖、密钥、代码和容器漏洞扫描。

### 16.6 安全监控

对登录异常、支付验签失败、金额差异、大额退款、敏感导出、WAF 拦截、5xx、任务积压、数据库容量和备份失败告警。

审计日志包含请求 ID、操作者、动作、资源、结果和时间，采用追加写入，普通后台账号无权修改。

安全响应流程：

```text
发现与告警
→ 判断影响
→ 撤销账号、令牌或来源
→ 隔离服务并轮换密钥
→ 保留证据
→ 修复和恢复
→ 履行必要通知
→ 复盘和补充检测
```

## 17. 可靠性与错误处理

- 所有外部平台调用设置连接、响应和总超时。
- 重试仅用于可安全重试的错误，并使用指数退避和随机抖动。
- 写操作通过幂等键保证重试安全。
- BullMQ 任务设置最大重试次数、死信处理和人工重放入口。
- Outbox 事件只有在消费者确认后才标记完成。
- 支付、通知和内容审核故障不会导致订单核心数据丢失。
- 非关键能力降级时，搜索和订单仍可使用。
- 服务关闭时停止接收新请求并等待进行中事务完成。

## 18. 备份与灾难恢复

- PostgreSQL 自动全量备份与日志备份，支持时间点恢复。
- COS 对重要桶启用版本控制或独立备份。
- 基础设施配置版本化，但密钥不进入仓库。
- 每季度将数据库恢复到隔离环境并核验订单、库存和文件关联。
- 每半年演练支付密钥泄露、数据库误删和账号被盗。
- RPO 目标 15 分钟，RTO 目标 2 小时；上线前通过演练验证。

## 19. 测试策略

### 19.1 自动测试

- 领域单元测试：定价、库存、订单状态、优惠和退款规则。
- 数据库集成测试：并发库存、事务回滚、唯一约束和迁移。
- API 契约测试：身份、权限、错误码和幂等。
- 前端组件测试：表单、错误状态和多语言。
- 端到端测试：搜索到预订、商家确认、退款和运营审核。
- 安全测试：越权、注入、XSS、SSRF、上传、暴力登录和回调伪造。

### 19.2 必测场景

- 两个用户争抢最后一间房。
- 多晚订单中任一日期无库存。
- 用户重复点击下单和支付。
- 支付成功但回调延迟或丢失。
- 回调重复、乱序或签名无效。
- 商家确认后用户超时未支付。
- 退款请求重复提交。
- 房源下架时存在未来订单。
- 中文内容缺少英文翻译。
- 商家试图访问其他商户订单。

## 20. 可观测性

每个请求和异步任务传递 `request_id`/`trace_id`。核心仪表盘包括：

- API 请求量、成功率、P50/P95/P99 延迟。
- 数据库连接、慢查询、锁等待和容量。
- Redis 命中率、内存和连接。
- 队列等待数、失败数和最长等待时间。
- 报价、库存锁、订单、支付和退款成功率。
- 外部支付、消息和内容审核平台延迟与错误。

日志进入 CLS，指标与链路遵循 OpenTelemetry 语义。日志写入前统一脱敏。

## 21. 分阶段路线图

### 阶段 0：基础与合规准备

- 企业主体、小程序账号、域名、备案和支付商户准备。
- 仓库、环境、CI、安全基线和基础设施。
- 隐私政策、协议、数据清单和权限模型。

退出条件：开发、预发布、生产边界明确，云账号与密钥权限可审计。

### 阶段 1：供给与管理后台

- 身份权限、商户、房源、房型、设施、媒体和多语言。
- 商家房态、价格日历和运营审核。

退出条件：运营可完整录入并发布一个真实房源，商家只能访问自身数据。

### 阶段 2：搜索与报价

- 小程序首页、搜索、筛选、附近房源、详情和报价。
- 基础排序、收藏和分享。

退出条件：用户可从搜索进入详情并获得服务端有效报价。

### 阶段 3：订单与支付

- 即时库存、人工确认、订单状态机、微信支付和退款。
- 超时释放、主动查单、通知和对账。

退出条件：并发测试无超卖，支付和退款全链路通过验签、幂等与对账测试。

### 阶段 4：运营闭环

- 客服、评价、优惠券、内容审核、财务和基础报表。
- 埋点、告警、审计和数据生命周期。

退出条件：运营可以独立处理异常订单、退款、投诉和对账差异。

### 阶段 5：多平台与规模化

- 支付宝、抖音适配与平台验收。
- 性能优化、只读实例或分析库评估。
- 根据业务指标评估 PMS/Channel Manager、ClickHouse 和服务拆分。

每个阶段在开始实施前分别形成可执行计划、风险清单和验收用例。本设计是平台总架构，不应被转换成一个跨越全部阶段的单次实施计划。

## 22. 上线检查清单

- 隐私政策、用户协议、商家协议和第三方共享清单已审核。
- 个人信息收集、保存、删除、注销和导出流程已验证。
- 支付回调验签、幂等、主动查单、退款和对账已演练。
- 并发库存测试证明不会超卖。
- 越权、注入、XSS、SSRF、上传和暴力登录测试通过。
- PostgreSQL、Redis 和 COS 均无不必要公网入口。
- 云账号 MFA、最小权限和密钥轮换已配置。
- 数据库恢复演练达到 RPO/RTO 目标。
- WAF、日志、指标和关键告警已验证。
- 已完成独立安全测试或渗透测试。
- 已定义生产事故联系人、升级路径和响应手册。

## 23. 关键技术决策摘要

| 决策 | 选择 | 原因 |
|---|---|---|
| 客户端 | Taro + React + TypeScript | 微信优先并兼容多小程序 |
| 管理后台 | React + Ant Design | 商家与运营共用，降低维护成本 |
| 后端 | NestJS 模块化单体 | 小团队可维护，保留清晰模块边界 |
| API | REST + OpenAPI | 交易与后台场景直接、可审计 |
| 数据库 | PostgreSQL 17 + PostGIS | 事务、复杂查询和地理搜索 |
| ORM | Prisma + 参数化 SQL | 常规类型安全，复杂场景保留 SQL 能力 |
| 缓存/队列 | Redis + BullMQ | 满足首期缓存、限流和任务需求 |
| 文件 | COS + CDN | 托管对象存储与图片分发 |
| 部署 | CloudBase Run + 腾讯云托管服务 | 减少服务器运维并支持扩缩容 |
| 分析 | PostgreSQL 聚合 + Metabase | 首期足够且成本低 |
| 安全基线 | OWASP ASVS 5.0 Level 2 | 适合含支付状态和敏感个人信息的平台 |
