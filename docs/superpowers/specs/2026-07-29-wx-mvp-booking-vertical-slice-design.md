# Stay Fable 微信最小预订闭环设计

状态：待用户书面复核  
日期：2026-07-29  
上位设计：`2026-07-28-wx-first-development-landscape-design.md`

## 1. 目标

本设计覆盖微信优先开发图景中的阶段 B、C、D，以可运行的纵向切片交付首个用户闭环：

```text
微信登录
→ 自动定位或手动选择城市
→ 选择入住日期、离店日期和人数
→ 浏览旅店
→ 查看旅店详情和房型
→ 获取服务端报价
→ 事务占用库存
→ 幂等创建待支付订单
→ 模拟支付
→ 查看订单
```

本轮完成后，项目应从微信模板页和后端健康检查基线，演进为可使用 PostgreSQL、
Redis、NestJS API、Worker 和原生微信小程序完成演示与自动化验收的最小住宿预订产品。

## 2. 范围

### 2.1 本轮包含

- 可切换的微信身份适配器，本地和测试使用确定性模拟身份。
- Redis 会话、会话续期和小程序请求层。
- 自动定位、运营城市归一化、定位失败回退和手动城市选择。
- 入住日期、离店日期和人数选择。
- PostgreSQL 版本化种子数据。
- 旅店列表、旅店详情、房型详情和基础筛选。
- 每日价格、5 分钟报价快照和报价变化处理。
- 每日库存、15 分钟库存占用和并发防超卖。
- 幂等创建订单、订单列表、订单详情和待支付订单取消。
- 开发专用模拟支付适配器。
- Worker 自动关闭超时待支付订单并释放库存。
- 微信编译、自动化主流程、预览和 WSL2 后端实机验证。

### 2.2 本轮不包含

- 真实微信 `code2session`、微信支付、退款和支付对账。
- 管理后台录入；本轮供给来自版本化种子数据。
- 商户账号、商户数据范围和运营审核。
- 地图找房、收藏、分享、评价、优惠券、会员和复杂排序。
- 英文或其他语言。
- 支付宝、抖音和 Taro 日常开发。
- 真实商户资料、手机号、证件或入住人敏感信息。

真实微信身份和支付保留适配器接口，但本轮不保存真实密钥，也不提供伪生产实现。

## 3. 交付方式

采用可运行纵向切片，不采用“全部后端完成后再开发小程序”或“先用页面假数据再回填
后端”的方式。

1. 身份、城市和搜索上下文。
2. 旅店、房型和种子供给。
3. 报价、库存占用和幂等下单。
4. 模拟支付、取消、订单查询和超时释放。
5. 全链路微信与 WSL2 验收。

每个切片同时交付数据库、API、小程序、测试和验证证据，不建立长期存在的第二套模拟
业务数据。

## 4. 系统结构

```text
/wx 原生微信小程序
├─ services：请求、会话、身份和业务错误
├─ stores：会话、城市、日期和人数
├─ pages：搜索、旅店、房型、确认和订单
└─ components：状态、价格、旅店卡片和表单组件
          │
          │ HTTPS REST /api/v1
          ▼
NestJS API 模块化单体
├─ Identity
├─ Location
├─ Catalog
├─ Pricing
├─ Inventory
└─ Booking
          │
          ├─ PostgreSQL 17 + PostGIS
          └─ Redis

独立 Worker
└─ 扫描并关闭超时待支付订单
```

PostgreSQL 是用户、供给、报价、库存、订单、支付和状态历史的事实来源。Redis 只保存
会话、限流和可重建的短期辅助数据，不承担最终库存和订单状态。

## 5. 后端模块边界

### 5.1 Identity

职责：

- 用平台登录码换取平台身份。
- 创建用户和 `user_identity`。
- 创建、续期、撤销 Redis 会话。
- 向请求上下文提供当前 `user_id`。

接口：

```text
WechatIdentityProvider
├─ MockWechatIdentityProvider
└─ Code2SessionWechatIdentityProvider
```

本轮只实现 `MockWechatIdentityProvider`。它接收测试登录码并稳定映射到模拟 `openid`，
使自动化测试可以创建两个相互独立的用户。`Code2SessionWechatIdentityProvider`
只定义接口和配置边界，不发起真实微信请求。

### 5.2 Location

职责：

- 返回已启用运营城市。
- 将经纬度归一化为最近的运营城市。
- 对不支持、超界或无效坐标返回稳定业务错误。

定位不是进入产品的强制条件。客户端拒绝授权、API 失败或无法匹配运营城市时，进入
手动城市选择。

### 5.3 Catalog

职责：

- 查询旅店和房型。
- 按城市、入住人数和旅店类型筛选。
- 返回旅店媒体、设施、政策和最低可售价格摘要。
- 保证房型始终从旅店详情进入，不作为一级搜索结果。

### 5.4 Pricing

职责：

- 查询入住区间内逐晚价格。
- 校验日期、入住人数、旅店营业状态和房型可售状态。
- 生成有 5 分钟有效期的报价快照。
- 下单前重新计算并识别报价变化。

### 5.5 Inventory

职责：

- 管理“房型 + 日期”的总库存、占用库存和已售库存。
- 在下单事务内按日期升序锁定库存。
- 创建、消费或释放每晚库存占用。
- 通过条件更新和数据库约束保证库存不为负且不超卖。

Redis 锁不能代替 PostgreSQL 事务。

### 5.6 Booking

职责：

- 使用幂等键创建订单。
- 保存旅店、房型、价格、政策和用户选择的必要快照。
- 执行订单状态机。
- 查询当前用户的订单。
- 取消待支付订单。
- 调用模拟支付适配器。
- 记录订单状态历史。

订单读取和写入都必须包含当前 `user_id`，不得仅凭订单 ID 操作资源。

## 6. 数据模型

### 6.1 身份和城市

| 表 | 关键字段和约束 |
| --- | --- |
| `user` | `id`、`status`、审计时间 |
| `user_identity` | `user_id`、`provider`、`provider_subject`；平台主体唯一 |
| `city` | 名称、行政编码、中心点、启用状态；行政编码唯一 |

会话保存在 Redis，使用高熵随机令牌。Redis 只保存令牌哈希、用户 ID、创建时间和到期
时间，不保存微信登录码。访问令牌过期后可使用轮换式刷新令牌续期；刷新失败则客户端
重新调用 `wx.login`。

### 6.2 旅店和房型

| 表 | 关键字段和约束 |
| --- | --- |
| `property` | 城市、类型、名称、地址、PostGIS 坐标、介绍、主图、营业状态 |
| `property_media` | 旅店、媒体类型、URL、排序 |
| `facility` | 稳定编码和中文名称 |
| `property_facility` | 旅店和设施联合唯一 |
| `room_type` | 旅店、名称、床型、面积、最大人数、图片、规则、销售状态 |

旅店类型首期固定为 `HOTEL`、`HOMESTAY`、`FARM_STAY`。

### 6.3 价格和库存

| 表 | 关键字段和约束 |
| --- | --- |
| `daily_price` | 房型、业务日期、销售价分、划线价分；房型和日期唯一 |
| `daily_inventory` | 房型、业务日期、总库存、占用库存、已售库存、版本号；房型和日期唯一 |
| `quote` | 用户、房型、日期、人数、逐晚明细 JSON、总价分、版本、到期时间 |

入住和离店使用 PostgreSQL `date`。技术时间戳使用 UTC。金额只使用整数分。

数据库约束至少保证：

```text
total_inventory >= 0
held_inventory >= 0
sold_inventory >= 0
held_inventory + sold_inventory <= total_inventory
sale_price_cents >= 0
checkout_date > checkin_date
```

### 6.4 订单

| 表 | 关键字段和约束 |
| --- | --- |
| `booking` | 用户、业务编号、状态、日期、人数、快照、总价分、幂等键、到期时间 |
| `inventory_hold` | 订单、房型、业务日期、状态、到期时间；订单和日期唯一 |
| `payment` | 订单、提供方、状态、金额分、模拟结果、唯一支付编号 |
| `booking_status_history` | 订单、原状态、目标状态、原因、操作者和时间 |

同一用户的下单幂等键唯一。业务编号、支付编号和库存占用业务键均使用数据库唯一约束。

## 7. 状态机与事务

### 7.1 报价

1. 校验城市、旅店、房型、人数和日期。
2. 查询每晚价格和库存。
3. 生成逐晚价格、总价、政策和版本。
4. 保存报价，5 分钟后失效。

列表和详情中的价格仅供展示。确认页必须重新请求报价。

### 7.2 下单

```text
读取报价
→ 校验用户、有效期和请求条件
→ 重新计算价格
→ 按日期升序锁定 daily_inventory
→ 校验每晚 available = total - held - sold
→ held_inventory 条件加一
→ 创建 booking
→ 创建每晚 inventory_hold
→ 写 PENDING_PAYMENT 状态历史
→ 提交事务
```

如果价格发生变化，返回 `QUOTE_CHANGED` 和新报价摘要；用户再次确认后使用新报价下单。
库存不足返回 `INVENTORY_UNAVAILABLE`。相同用户和幂等键重放时返回原订单。

### 7.3 模拟支付

模拟支付路由只在开发或测试环境且 `ENABLE_MOCK_PAYMENT=true` 时注册。生产环境设置该
开关必须启动失败。

模拟成功在一个数据库事务中完成：

1. 锁定订单、支付和库存占用。
2. 校验订单为 `PENDING_PAYMENT` 且未过期。
3. 写支付成功。
4. 每晚 `held_inventory - 1`、`sold_inventory + 1`。
5. 将占用标记为已消费。
6. 依次记录 `PAID`、`CONFIRMED` 状态历史。

模拟失败只记录支付失败尝试，订单仍保持待支付。

### 7.4 取消和超时

- 用户只能主动取消自己的 `PENDING_PAYMENT` 订单。
- 已确认订单本轮不提供退款，界面提示联系客服。
- Worker 使用 `FOR UPDATE SKIP LOCKED` 批量领取过期订单。
- 释放事务会减少每晚占用库存、标记占用已释放、关闭订单并写状态历史。
- 已关闭、已取消或已消费的占用重复处理时直接返回成功，不再次调整库存。

时间相关服务注入 `Clock`，测试通过推进时间验证 5 分钟报价和 15 分钟订单，而不真实
等待。

## 8. API 设计

所有 API 使用 `/api/v1` 前缀。成功响应：

```json
{
  "data": {},
  "request_id": "req_01..."
}
```

失败响应：

```json
{
  "error": {
    "code": "QUOTE_EXPIRED",
    "message": "报价已失效，请重新获取"
  },
  "request_id": "req_01..."
}
```

### 8.1 身份和城市

```text
POST /api/v1/auth/wechat/login
POST /api/v1/auth/session/refresh
GET  /api/v1/cities
POST /api/v1/location/resolve
```

登录请求只包含微信登录码。定位请求包含经纬度，服务端校验数值范围；日志不记录原始
精确坐标。

### 8.2 旅店和房型

```text
GET /api/v1/properties
GET /api/v1/properties/:propertyId
GET /api/v1/room-types/:roomTypeId
```

列表参数包含 `city_id`、`checkin`、`checkout`、`guests`、可选 `property_type` 和
`cursor`。排序首期固定为可售优先，其后按种子数据中的展示顺序，不建设个性化排序。

### 8.3 报价和订单

```text
POST /api/v1/quotes
POST /api/v1/bookings
GET  /api/v1/bookings
GET  /api/v1/bookings/:bookingId
POST /api/v1/bookings/:bookingId/cancel
POST /api/v1/dev/payments/:bookingId/simulate
```

创建订单必须携带 `Idempotency-Key`。订单列表使用游标分页。模拟支付请求显式选择
`SUCCEED` 或 `FAIL`，路由同时受环境、功能开关、登录用户和订单归属校验。

## 9. 稳定业务错误

- `AUTH_SESSION_EXPIRED`
- `AUTH_REFRESH_REJECTED`
- `CITY_NOT_SUPPORTED`
- `PROPERTY_NOT_AVAILABLE`
- `ROOM_NOT_AVAILABLE`
- `ROOM_CAPACITY_EXCEEDED`
- `QUOTE_EXPIRED`
- `QUOTE_CHANGED`
- `INVENTORY_UNAVAILABLE`
- `BOOKING_ALREADY_PROCESSED`
- `BOOKING_NOT_CANCELLABLE`
- `BOOKING_NOT_FOUND`
- `MOCK_PAYMENT_DISABLED`
- `MOCK_PAYMENT_FAILED`

服务端不返回内部堆栈、数据库错误或第三方原始错误。每个错误保留 `request_id`。

### 10.1 目录职责

```text
wx/
├─ services/
│  ├─ request.js
│  ├─ auth.js
│  └─ booking.js
├─ stores/
│  ├─ session.js
│  └─ search.js
├─ utils/

│  ├─ money.js
│  └─ idempotency.js
├─ components/
│  ├─ loading-state/
│  ├─ empty-state/
│  ├─ error-state/
│  ├─ price/
│  └─ property-card/
└─ pages/
   ├─ home/
   ├─ city-select/
   ├─ date-guest-select/
   ├─ property-list/
   ├─ property-detail/
   ├─ room-detail/
   ├─ booking-confirm/
   ├─ order-list/
   └─ order-detail/
```

不在小程序内复制后端价格、库存或状态机规则。首期直接使用 REST JSON，不引入复杂的
微信 npm 共享包。

### 10.2 页面流

- 首次进入自动登录。失败时显示重试，不展示伪登录成功。
- 定位授权前解释用途。拒绝、失败或超时进入城市选择。
- 默认入住为次日、默认一晚、默认 2 人。
- 首页提交城市、日期和人数后进入旅店列表。
- 旅店列表只显示旅店；进入详情后才显示房型。
- 房型详情进入确认页前请求报价。
- 确认页下单期间锁定按钮，并使用稳定幂等键。
- 订单详情可以模拟成功、模拟失败或取消待支付订单。

### 10.3 状态和重试

每个页面必须覆盖加载、空数据、无权限、网络失败和未知错误。

- 查询请求可在网络错误时手动重试；只有确定幂等的查询允许有限自动重试。
- 下单、模拟支付和取消不自动重试。
- 会话 401 只允许一次受控刷新和原请求重放。
- 报价变化展示旧价、新价和原因，必须由用户再次确认。
- 页面失败后保留城市、日期、人数和已加载的安全展示数据。

### 10.4 视觉边界

本轮提供可演示的精简成品体验：

- 暖色住宿主题和统一设计变量。
- 清晰的旅店、房型、价格和订单信息层级。
- 触控区域不小于 44px。
- 使用统一加载、空态和错误组件。

本轮不建设完整品牌规范或通用组件平台。

## 11. 种子数据

版本化种子数据包含：

- 2 个运营城市。
- 每个城市 3 家旅店，覆盖酒店、民宿和农家乐。
- 每家旅店 2 个房型。
- 每个房型未来 60 天价格和库存。
- 至少一个总库存为 1 的并发测试房型。
- 可重复执行且结果确定，不创建重复记录。

图片使用明确允许公开使用的固定测试资源或仓库内测试素材。种子数据不得包含真实
商户、手机号、精确私人住址或个人资料。

## 12. 安全和配置

- 模拟身份和模拟支付生产环境强制禁用。
- 会话令牌、刷新令牌和微信登录码不写日志。
- 写接口验证身份、资源归属、业务状态和幂等键。
- DTO 校验字符串长度、枚举、日期范围、人数和坐标范围。
- 数据访问使用 Prisma 或参数化 SQL。
- 库存锁定 SQL 固定表名和字段，不拼接用户输入。
- 日志记录 `request_id`、业务错误码和内部资源 ID。
- 小程序本地不保存个人敏感资料。
- CORS、HTTPS 和真实微信域名配置属于上线阶段；本轮开发环境仍保持明确允许列表。

## 13. 测试策略

### 13.1 单元测试

- 本地日期和人民币分格式化。
- 报价逐晚计算、总价和有效期。
- 订单状态机。
- 幂等键生成和重复请求处理。
- 库存可售数量和释放规则。
- 模拟适配器的生产环境拒绝规则。

### 13.2 API 和数据库测试

- 登录、续期、未授权和用户隔离。
- 城市列表、定位匹配和不支持城市。
- 旅店分页、人数和类型筛选。
- 报价过期、价格变化和无库存。
- 相同幂等键只产生一个订单。
- 两个用户争抢最后一间房时只有一个成功。
- 多晚订单任一日期无库存时事务整体回滚。
- 取消订单和 Worker 释放不会重复调整库存。
- 用户无法读取、支付或取消其他用户订单。

PostgreSQL 集成测试使用真实 PostgreSQL/PostGIS，不用 SQLite 替代事务和锁行为。

### 13.3 Worker 测试

- 时钟推进超过 15 分钟后关闭待支付订单。
- 重复执行不重复释放。
- 两个 Worker 并发领取不会处理同一订单。
- 单个订单失败不阻断其他订单，失败有结构化日志。

### 13.4 微信验收

- 每个切片运行 `pnpm wx:check` 和微信开发者工具编译。
- 主流程完成后使用 `automator` 验收关键页面。
- 生成一次微信预览，不上传体验版。
- 定位拒绝路径必须作为独立用例。

### 13.5 WSL2 验收

遵循 `docs/operations/wsl-runtime-validation.md`：

- PostgreSQL/PostGIS 查询成功。
- Redis 返回 `PONG`。
- API live/ready 返回 HTTP 200。
- API 和 Worker 为非 root、只读根文件系统。
- Worker 观察至少 10 分钟，重启为 0 且无重连循环。
- 临时容器和产物被清理，数据卷默认保留。

## 14. 最终验收

主流程：

```text
模拟微信登录
→ 拒绝定位
→ 手动选择城市
→ 设置日期和人数
→ 浏览旅店
→ 进入旅店详情
→ 选择房型
→ 获取报价
→ 重复点击下单
→ 只产生一个待支付订单
→ 模拟支付成功
→ 订单列表和详情显示已确认
```

还必须证明：

- 自动定位成功路径可选择匹配城市。
- 两个用户争抢最后一间房不会超卖。
- 报价过期或变化不能直接下单。
- 待支付订单取消后库存恢复。
- Worker 超时释放可重复执行。
- 用户不能访问其他用户订单。
- 生产配置不能启动模拟身份或模拟支付。
- `/wx` 官方编译和预览成功。

## 16. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 原生微信端缺少共享类型 | OpenAPI 和契约测试作为协议事实来源，首期不引入复杂构建 |
| 模拟能力误入生产 | 环境与功能开关双重保护，生产启动时主动拒绝 |
| 日期和时区错误 | 入住日期使用数据库 `date`，客户端使用本地日期工具 |
| 库存并发超卖 | 固定日期锁顺序、条件更新、约束和真实 PostgreSQL 并发测试 |
| Worker 重复释放 | 状态条件、行锁和幂等占用状态 |
| 计划跨越模块过大 | 按五个纵向切片实施，每个切片独立验收和提交 |
| 已知依赖漏洞 | `dev` 持续报告；进入 `release/main` 前修复或获得正式风险例外 |

本规格只定义首个微信预订 MVP，不改变真实支付、管理后台、多平台和上线合规的后续
阶段边界。
