# Stay Fable 微信优先开发图景设计

状态：已完成方案讨论，待书面复核
日期：2026-07-28
目标：将正式用户端收敛到原生微信小程序，并建立可持续的微信与 WSL2 验证工作流

## 1. 决策摘要

Stay Fable 后续开发以仓库根目录的 `/wx` 原生微信小程序为唯一正式用户端。
`apps/consumer-miniapp` 中的 Taro 多平台工程保留为历史参考，但冻结开发，不再参与
默认构建、日常质量门禁或发布流程。支付宝、抖音和多语言能力整体移入远期路线。

后端继续采用 NestJS 模块化单体、PostgreSQL/PostGIS、Redis 和独立 Worker。管理后台
继续保留，但在微信用户端首个闭环完成前只实现支撑供给录入所必需的能力。

依赖漏洞不再阻断 `dev` 阶段的功能开发，但扫描和报告必须持续执行。进入 `release`
前，Critical 和 High 漏洞必须修复，或由规定角色审批有期限的风险例外。

## 2. 已评估方案

### 2.1 原生微信主线

将 `/wx` 作为正式客户端，直接使用微信原生组件、生命周期和 API。优点是官方工具
兼容性最好、调试路径最短、首期开发负担最低。缺点是未来增加其他平台时需要重新
评估客户端实现。

### 2.2 Taro 微信单平台

保留 Taro 工程但只构建微信端。优点是继续复用已有跨平台结构；缺点是即使不发布
其他平台，仍需承担跨平台抽象、Webpack/Taro 依赖和构建链维护成本。

### 2.3 原生微信与大量共享包

原生微信界面与 workspace 内共享协议、校验和业务模型深度集成。长期边界清晰，但
首期需要额外解决模块格式、打包、微信 npm 构建和调试问题。

最终选择方案 2.1。首期只通过 REST/OpenAPI 约定复用接口协议，不立即建设复杂的
微信端共享包体系。

## 3. 产品信息架构

平台以“旅店”为一级展示和交易入口。酒店、民宿、农家乐都是旅店的业务类型。
用户进入旅店详情后，才查看和选择其房型或房源。

```text
城市
└─ 旅店（酒店 / 民宿 / 农家乐）
   ├─ 名称、类型、位置、评分、设施、介绍和图片
   └─ 房型/房源
      ├─ 名称、床型、面积、可住人数和图片
      ├─ 每日价格和库存
      └─ 取消政策与预订规则
```

首个用户闭环固定为：

```text
微信登录
→ 自动定位或手动选择城市
→ 选择入住日期、离店日期和人数
→ 浏览或搜索旅店
→ 查看旅店详情
→ 选择房型
→ 获取服务端报价
→ 创建待支付订单
→ 模拟支付
→ 查看订单
```

首期不建设地图找房。定位失败、用户拒绝定位或微信 API 不可用时，必须回退到手动
选择城市。

## 4. 系统边界

```text
/wx 原生微信小程序
        │ HTTPS REST
        ▼
NestJS API 模块化单体
├─ Identity：微信登录和用户会话
├─ Location：城市和定位结果归一化
├─ Catalog：旅店、房型、设施和图片
├─ Pricing：每日价格和报价快照
├─ Inventory：每日库存和占用
└─ Booking：订单、取消和模拟支付
        │
        ├─ PostgreSQL 17 + PostGIS
        ├─ Redis
        └─ Worker
```

微信端不得自行决定最终价格、库存或订单状态。写操作使用幂等键；价格或库存发生
变化时，服务端返回明确业务错误，客户端展示新报价并要求用户重新确认。

## 5. 核心数据模型

| 实体              | 职责                                                                 |
| ----------------- | -------------------------------------------------------------------- |
| `city`            | 可运营城市、显示名称、行政编码和启用状态                             |
| `property`        | 旅店类型、城市、地址、坐标、介绍、设施、主图和营业状态               |
| `room_type`       | 所属旅店、床型、面积、入住人数、图片和预订规则                       |
| `daily_price`     | 房型、日期、销售价、划线价和适用价格计划                             |
| `daily_inventory` | 房型、日期、总库存、已售库存和临时占用库存                           |
| `quote`           | 用户查询条件、逐晚价格、总价、取消政策、版本和有效期                 |
| `booking`         | 用户、旅店、房型、入住日期、人数、报价快照、业务编号和订单状态       |
| `payment`         | 首期模拟支付记录；后续承载微信支付交易号、回调状态和幂等处理结果     |

金额统一以人民币分保存。旅店和房型的展示信息在订单中保存必要快照，避免后续内容修改
改变历史订单。库存以“房型 + 日期”作为唯一业务粒度。

## 6. 微信端组件边界

`/wx` 至少划分以下职责：

- `services/`：统一请求、会话续期、业务错误和请求 ID。
- `stores/`：登录态、城市、日期和人数等跨页面状态。
- `pages/home/`：城市、日期、人数和旅店推荐入口。
- `pages/property-list/`：旅店列表、搜索、筛选和分页。
- `pages/property-detail/`：旅店内容、设施及房型列表。
- `pages/room-detail/`：房型信息、价格日历和预订规则。
- `pages/booking-confirm/`：服务端报价确认和幂等下单。
- `pages/order-list/`、`pages/order-detail/`：订单查询、模拟支付和取消。
- `components/`：加载、空状态、错误、价格、日期和旅店卡片等通用组件。

所有页面必须具备加载、空数据、无权限、网络失败和未知错误状态。只有幂等查询允许
自动重试；下单、取消和支付不得由客户端自动重试。

## 7. 开发阶段

### 阶段 A：工程重整

- 新增根目录 `AGENTS.md`，固化微信技能、WSL2 后端验证、分支和漏洞策略。
- 将旧工作树中尚未提交的 4 份文档完整整合到主线。
- 将 Taro 多平台构建移出默认门禁，但保留代码。
- 为 `/wx` 增加配置、页面声明、静态检查和微信工具编译验收。
- 清理旧工作树和已完成功能分支，并同步远程 `main`、`dev`、`release`。

退出条件：所有本地工作树 `git status` 干净；所有保留文件均已提交并推送；三条远程
基线分支指向同一整理提交。

### 阶段 B：微信基础体验

- 微信登录和后端会话。
- 自动定位、城市回退和手动切换。
- 入住日期、离店日期和人数选择。
- 请求层、会话续期、错误状态和基础设计变量。

退出条件：微信开发者工具中可完成登录、城市和日期人数选择，拒绝定位时仍可继续。

### 阶段 C：旅店与房源

- 城市、旅店、房型、设施、图片、价格和库存数据结构。
- 旅店列表、搜索筛选、旅店详情和房型列表。
- 平台自营种子数据和最小录入能力。

退出条件：用户可以从城市入口进入旅店列表，打开旅店并选择可售房型。

### 阶段 D：订单闭环

- 报价快照、库存校验、幂等下单。
- 订单列表、订单详情、取消和模拟支付。
- 订单和库存状态测试。

退出条件：用户能够完成“旅店 → 房型 → 报价 → 下单 → 模拟支付 → 查订单”。

### 阶段 E：供给运营

- 管理后台录入旅店、房型、图片、价格和库存。
- 平台运营审核与上下架。
- 商家数据范围和最小角色权限。

退出条件：运营人员无需修改数据库即可维护一个完整可售旅店。

### 阶段 F：微信上线准备

- 真实微信支付、验签回调、主动查单和退款。
- 订阅消息、隐私授权、业务域名和备案配置。
- 备份、监控、告警、依赖漏洞和发布审批。

退出条件：真实支付沙箱或受控金额全链路通过，所有 `release` 门禁获得证据。

### 远期搁置

- 支付宝和抖音小程序。
- 英文和其他语言。
- 地图找房、评价、复杂营销和会员积分。
- 多商户自动分账、PMS/Channel Manager 和复杂数据分析。

## 8. `AGENTS.md` 工作流

仓库根目录 `AGENTS.md` 是每项开发开始前的必读规则：

1. `/wx` 是唯一正式用户端，微信相关工作必须选择适用的 wechatide 技能。
2. 打开项目和环境检查使用 `initializer`。
3. 编译和模拟器刷新使用 `compiler`。
4. 手机预览使用 `previewer`。
5. 页面交互验收使用 `automator`。
6. 日志、网络、截图和运行问题使用 `debugger`。
7. 项目设置变更使用 `project-config`。
8. 后端实机验证默认在 WSL2 `Ubuntu-22.04` 的 Docker Engine 中完成。
9. WSL2 验证必须覆盖 PostgreSQL/PostGIS、Redis、API 就绪、Worker、非 root 用户和
   只读文件系统。
10. 默认端口冲突时使用宿主端口 `55432` 和 `56379`，不得停止无关容器。
11. 临时验证容器和文件在任务结束时清理，数据库卷默认保留。
12. `dev` 阶段漏洞扫描仅报告；`release` 阶段恢复强制门禁。

## 9. 分支和发布规则

- `dev` 是日常集成分支。
- 新工作从 `dev` 创建 `codex/<feature>` 分支。
- 功能分支通过测试和微信工具验收后合入 `dev`。
- `release` 只接收已验收的 `dev` 提交，并执行完整发布门禁。
- `main` 只接收正式发布版本。
- 禁止强制推送共享分支。
- 删除工作树或分支前，必须确认所有修改已提交、已整合且已上传。

本次工程重整完成时，`main`、`dev`、`release` 允许暂时指向同一基线提交。之后按上述
职责分别推进。

## 10. 验证策略

### 默认开发门禁

- 仓库格式、lint、类型检查、单元测试和构建。
- `/wx` JSON 配置、页面文件、引用资源和静态规则检查。
- 微信开发者工具编译。
- 受影响后端模块测试。
- WSL2 中的 PostgreSQL、Redis、API 和 Worker 运行验证。
- 依赖漏洞扫描生成报告，但不改变 `dev` 验证结果。

### Release 门禁

- 默认开发门禁全部通过。
- 微信开发者工具预览及关键页面自动化。
- PostgreSQL 集成测试、API 就绪和 Worker 稳定性。
- API/Worker 非 root、只读文件系统和生产配置验证。
- Critical/High 漏洞清零，或存在批准人、到期日和缓解措施明确的例外。
- 真实微信支付、隐私、备份、监控和运营验收证据。

## 11. 错误与降级

- 定位拒绝或失败：显示城市选择页。
- 会话过期：静默换取新会话；失败后回到明确登录状态。
- 旅店列表失败：保留查询条件并提供手动重试。
- 房型无库存：禁止进入确认页并推荐返回日期选择。
- 报价变化：显示旧价和新价，只有用户再次确认后才下单。
- 重复下单：服务端使用幂等键返回已有结果。
- 模拟支付失败：订单保持待支付，可从订单详情再次发起。
- Worker 或非核心依赖异常：不破坏已提交的订单事务，记录可重放任务。
