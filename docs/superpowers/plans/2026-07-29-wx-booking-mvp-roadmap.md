# 微信预订 MVP 开发路线图

状态：已确认设计后的执行路线  
日期：2026-07-29  
设计依据：`docs/superpowers/specs/2026-07-29-wx-mvp-booking-vertical-slice-design.md`

## 目标

以 `/wx` 为唯一正式客户端，用五个可独立验收的纵向切片完成：

```text
登录与搜索上下文
→ 旅店与房型浏览
→ 报价与并发安全下单
→ 支付、取消与超时释放
→ 微信和 WSL2 全链路证据
```

每个切片同时修改数据库、NestJS API、原生微信小程序、测试和运行文档。后一个切片只在
前一个切片的退出门禁通过后开始，避免长期维护页面假数据或第二套业务规则。

## 切片路线

| 切片 | 用户可见结果 | 后端核心 | 退出门禁 |
| --- | --- | --- | --- |
| 1. 身份与搜索上下文 | 自动登录、定位回退、城市/日期/人数选择 | 统一 API 协议、Redis 会话、用户/城市、PostGIS 定位 | 微信官方编译；登录续期、城市解析和回退测试；WSL API/Redis/PostGIS 验证 |
| 2. 供给浏览 | 城市旅店列表、旅店详情、房型详情 | 旅店/房型/媒体/设施、60 天确定性种子、可售摘要 | 只以旅店为一级；筛选/分页测试；每城 3 店、每店 2 房型 |
| 3. 报价与下单 | 确认价格并创建待支付订单 | 5 分钟报价、库存行锁、15 分钟占用、幂等订单 | 重复点击只有一单；两用户争抢最后一间只成功一个；多晚回滚 |
| 4. 生命周期 | 模拟支付、取消、订单列表/详情 | 状态机、支付记录、历史、Worker 超时释放 | 用户隔离；取消恢复库存；Worker 并发和重复执行安全 |
| 5. 全链路证据 | 可自动化演示和手机预览 | OpenAPI 契约核验、生产模拟能力门禁 | automator 主流程、预览、WSL 10 分钟观察、完整质量门禁 |

## 计划文件策略

- 当前详细执行计划：
  `docs/superpowers/plans/2026-07-29-wx-booking-slice-1-identity-search.md`
- 切片 2–5 在各自开始前，根据前一切片已经稳定的接口和数据模型生成详细计划。
- 若切片退出门禁暴露架构偏差，先更新已确认设计的“决策变更”章节，再规划下一切片。
- 真实微信身份、真实支付、管理后台和多平台继续留在后续里程碑，不插入本路线。

## 全程固定规则

- `/wx` 每个切片至少执行 `pnpm wx:check` 和微信开发者工具官方编译。
- PostgreSQL 锁与约束测试必须使用真实 PostgreSQL/PostGIS，不用 SQLite 替代。
- Worker 与 API 最终按 `docs/operations/wsl-runtime-validation.md` 在 Ubuntu-22.04 验证。
- `dev` 阶段漏洞只报告；进入 `release/main` 前 Critical/High 必须修复或有正式风险例外。
- 每个任务遵循红灯测试、最小实现、绿灯验证和原子提交。
